# 審查與修復循環（review → fix → verify）

目的：**在問題變成客訴之前發現它**。這份文件是流程，`npm run review` 是自動化的一半；
另一半是每一次改動都要問的那幾個問題。

## 三種節奏

| 節奏 | 何時 | 做什麼 | 指令 |
|---|---|---|---|
| 每次改動 | commit 前 | 單元測試 ＋ 對抗式探針 | `npm test && npm run review` |
| 每次發佈 | 升版前 | 乾淨 profile 端到端（安裝→組合→啟動→payload→安全矩陣→UI） | 見 `docs/acceptance-*.md` 的檢查表 |
| 定期審計 | 每週或每個里程碑 | 逐功能重讀實作、重跑探針、更新台账 | `npm run review` ＋ 手動清單 |

## 每次改動的循環

1. **選一個功能面**（不要一次審全部）。
2. **問對抗式問題**（見下表），至少三個。
3. **把假設變成實驗**：能在 60 秒內用 Node 腳本或 curl 重現的，就做實驗，不要推理。
4. **分級**（見 rubric），寫進 `docs/review-findings.md`。
5. **修**：程式＋**回歸測試**（測試名稱帶發現編號，例如 `S1: …`）。
6. **重跑** `npm test && npm run review`，必要時再跑一次 E2E。
7. **更新台账**：open → fixed，附證據。

## 對抗式問題清單（按功能類別）

| 類別 | 必問 |
|---|---|
| 會寫入 / 安裝的動作 | 中途失敗會留下什麼？誰負責還原？有沒有驗證「動作前的狀態」？並發兩次會怎樣？ |
| 狀態檔案 | 記錄與實際狀況不同時會怎樣？多個行程同時寫？檔案損毀？ |
| 對外分享的產物 | 會不會帶出絕對路徑、使用者名稱、token、內部主機名？ |
| 讀取端點 | 未授權的人能讀到什麼？經過隧道／LAN 時還安全嗎？ |
| 前端生命週期 | 卸載時清理了什麼？effect 的 disposer 交回去了嗎？服務沒 inject 會炸嗎？ |
| 背景掃描 | 掃多大？上限在哪？跨專案／跨使用者資料會不會混進來？ |
| 時間 / 時區 | 用誰的時鐘？跨時區的使用者看到什麼？ |
| 提示與文案 | 有沒有把「未確認」說成「已確認」（例如 registry 失敗卻說已是最新）？ |

## 嚴重度 rubric

| 級別 | 判準 | 處理 |
|---|---|---|
| **P0** | 資料遺失、無法啟動、未授權寫入 | 立刻修，擋發佈 |
| **P1** | 隱私外洩、誤導性狀態、可重現的錯誤行為 | 擋發佈 |
| **P2** | 有替代路徑的缺陷、明顯 UX 破口、資源上限缺失 | 本次或下次修 |
| **P3** | 美觀、文案、測試覆蓋缺口 | 排入 backlog |

## 自動化：`npm run review`

`scripts/review.mjs` 是**獨立於單元測試**的探針：即使某個測試被刪掉，這裡仍會抓到回歸。
每個探針輸出 PASS/FAIL 與一行證據，全部通過才 exit 0。

目前 10 個探針覆蓋：回滾失敗還原、stale 記錄拒絕、診斷包去識別化、accent disposer、
locale 解析、預覽載入中禁止確認、設定變更通知徽章、使用量上限與範圍、失敗紀錄、
插件徽章降級。

## 台账

所有發現（含未修與已知限制）記在 [`docs/review-findings.md`](review-findings.md)。
每次審計只追加、不刪除；修好的標 `fixed` 並附測試／探針編號。
